# Identity and access (kernel module B1)

Who may act, on which device, in which role, with which qualification, and how every command and
signature is tied to one real person. Schema `iam`, migrations `packages/kernel/sql/0100`–`0190`,
TypeScript in this folder, tests in `packages/kernel/test/identity/`.

Controls: DI-14 to DI-21. Invariants: INV-11, INV-26, INV-40 and the "user IDs never reused" part of
INV-27. Outline 4.7, 5.5, 7.1, 7.2, 7.4; ADR 0001, 0006, 0012.

**Where the data will live.** Phase 1 builds identity inside the kernel and tests it in one
database. In the site topology (ADR 0001) persons, accounts, credentials, badges, qualifications and
devices belong to the site-services database; each edition database will hold freshness-bounded
mirrors of them, and guards that read a mirror fail closed when it is stale (INV-38). The mirror
heartbeat stub (`iam.mirror_heartbeat`) already shows that pattern for qualifications.

## Roles in the database

| Role | Can do |
|---|---|
| `ebmr_owner` | Owns every table and function (NOLOGIN). |
| `ebmr_app` | Reads non-secret IAM tables and calls the IAM functions granted to it. No INSERT, UPDATE or DELETE on any IAM table; cannot read verifiers, badge hashes or authentication attempts; cannot create authentication events. |
| `ebmr_authn` | The authentication service (ADR 0012 decision 1). EXECUTE on `iam.authn_prepare`, `iam.authn_finish`, `iam.authn_secret_history`, `iam.authn_change_secret`, `iam.resolve_device` and the policy getters only; no table privileges. The only path that reads a verifier (for the account being authenticated) or creates an authentication event. Created by migration 0100 (dev password `ebmr_authn`; production credentials come from the vault). |

**Secrets and the audit trail.** Each credential is two rows: `iam.credential` holds only metadata
(kind, origin, must-change flag, status, expiry, issuer) and is audited on the account chain, so
every issue, reset, change and revocation is in the hash-chained trail; `iam.credential_secret`
holds the argon2id verifier, is not audited (audit diffs must never contain verifiers), is
insert-only, and nobody but `ebmr_owner` has any privilege on it. A secret is never updated in
place: a new secret is a new credential row plus a new secret row. Badge UIDs are stored only as a
peppered SHA-256 in `iam.badge_secret`. Plaintext exists only in the authentication service's
memory; initial and reset secrets are generated by the service and delivered to the owner, never
shown to the administrator, are single-use, expire, and must be changed before the account can
sign or open a session. The database refuses any verifier that is not argon2id v19 with at least
m=19456 KiB, t=2, p=1.

**Protected logs.** Authentication attempts and events, lock events, sessions, alerts and the
command log are written before anyone is authenticated, so they are not in the hash-chained audit
trail (which needs an actor). They are insert-only for every role (triggers), unwritable by
`ebmr_app`, and every command's audit events carry the session and authentication-event IDs that
point back to them. Human acts on them (alert acknowledgement and escalation, unlock) are audited.

## What other modules call

TypeScript (`@ebmr/kernel` once the lead exports `./identity/index.ts`):

- `authenticate(authnDb, {method, identifier, secret?, deviceFingerprint, purpose, challengeId?})` →
  single-use authentication event. Methods `PASSWORD`, `BADGE_PIN`, `BADGE_TAP` (per-entry
  attribution only), `SERVICE_KEY`; purposes `LOGIN`, `COMMAND`, `SIGNATURE` (with challenge),
  `CREDENTIAL_CHANGE`, `SESSION_UNLOCK`. `changeSecret(...)`.
- `openSession`, `lockSession`, `unlockSession`, `keepSessionAlive`, `endSession`, `resolveDevice`,
  `assertDeviceLocation`, `deviceFingerprint`.
- `evaluateAuthority`, `requirePermission`, `authorize`, `withGuardedCommand` (logs refusals).
- Administration wrappers in `admin.ts` (persons, identity checks, accounts, grants, devices,
  badges, initial secrets, qualifications, policy).

SQL (inside a command started with `kernel.begin_command`):

- `iam.require_permission(permission, scope)` — the actor, in its declared role, holds the
  permission in that scope now, with its required qualifications; refusal EBMR-IAM-040 with a JSON
  DETAIL. Pass the full scope of the object (`{"site":…, "area":…, "product":…}`).
- `iam.evaluate_authority(person, account, permission, scope, at, role)` — stored evaluation
  (INV-26); returns `evaluation_id` to store with a signature or data point.
- `iam.assert_not_administrator()` — call in every GMP data write path (DI-18).
- `iam.assert_segregated(rule, excluded_persons, subject)` with `iam.record_entry_persons(table,
  id)` or `iam.chain_persons(chain_key)` — dynamic segregation on the person (EBMR-IAM-041).
- For the signing module (B2): `iam.consume_auth_event(event, expected_person,
  expected_challenge, max_age)` (owner-only; single use, same person, same challenge, fresh; may
  share the event with its own command's attribution), `iam.assert_can_sign(account)`,
  `iam.resolve_signer(account, at)`, `iam.delegation_valid(delegation, person, meaning, scope,
  market, at)`, `iam.current_command_auth_event()`.
- `iam.assert_us_esig_certification(legal_entity)` — before issuing a batch with US in its
  market set (BLOCK or FLAG per policy `esig.us_certification_mode`).
- `iam.access_list(at)`, `iam.signature_register(at)`, `iam.recertification_due(at)`,
  `iam.badges_due_for_test(at)`, `iam.directory_scan()` (invariant query; zero rows expected).
- For the continuity module (INV-27 user IDs after a restore): `iam.issued_login_names()` lists every
  login name issued here or reserved (the anchor job copies it to the external ledger), and
  `iam.reserve_identifiers(names jsonb, reason, restore_event)` (owner-only, for `continuity.after_restore`
  inside its validated command) reserves the ledger's names this database no longer knows, so
  `iam.create_account` refuses them (EBMR-IAM-021).

Every function that changes an existing row needs `reason_code` in the actor context (kernel audit
rule EBMR-AUDIT-002).

## Changing a role's permissions (DI-16, DI-18, INV-11)

Adding a permission to a role grants it to every holder, so it follows the rule of every grant: one
person requests it (`iam.add_role_permission(role, permission, reason)`, IAM.ROLE_MANAGE; the reason
defaults to the command's reason text) and a second person approves or rejects it
(`iam.decide_role_permission(request, approve, reason)`, IAM.GRANT_APPROVE). Only the approval adds the
`role_permission` row. Neither the requester nor the approver may hold the role (EBMR-IAM-003,
EBMR-IAM-032): administrators never grant themselves authority. Removing a permission
(`iam.remove_role_permission`) takes authority away and is effective at once, like a revocation. Inside a
command even the table owner adds a row only through an approved request; outside a command only a
software release (`SOFTWARE_RELEASE` identity, as in 0700) does (EBMR-IAM-039). Role names and bundles
stay customer configuration (features spec A.7); versioned change control of all configuration (DI-09)
comes later.

The static rules (a role never mixes administration and GMP permissions, every holder is re-checked)
run at the request and again at the approval. Every static check locks the role before the person: a
catalogue change takes the role exclusively and its holders' person rows in person order; a grant
request or approval takes the granted role in share mode, then the person, then the account in share
mode (the order `iam.process_leaver` uses), so a deactivation, suspension or leaver either waits for
the approval and then revokes the new grant too, or is seen and the approval is refused. A grant is
approved only for an ACTIVE account (EBMR-IAM-026); a request may be raised during onboarding. The catalogue is then
read as it stands once the locks are held (live now), so concurrent changes are checked one after the
other and none can leave a role or a person with both domains. `iam.check_static_segregation` also
refuses a role that holds both domains, and `iam.directory_scan()` reports such a role
(`ROLE_MIXES_ADMINISTRATION_AND_GMP`) and any grant of it (`ADMINISTRATOR_AND_GMP_ROLE`).

## Authority checks in the other modules (B7, migrations 0700 and 0710)

**Catalogue.** `0700_authorization_catalogue.sql` adds the permissions of the market, records,
continuity, site-services (batch-number register) and platform modules and maps them to the kernel
roles (the full map is in each module's README and in
`test/integration/authorization.test.ts`). GMP data permissions are domain GMP, so INV-11 keeps every
holder away from administrator roles; pure IT functions (restore operation, kiosk hardening, time
sources) are ADMINISTRATION and held by the system administrator; oversight functions (backup
catalogue, continuity alarms, platform settings, time-alarm clearance) are GOVERNANCE. Service
accounts hold WRITE effects only. The catalogue tables are audited, so the rows are written under a
labelled pipeline identity (nil person, account and session; role and reason `SOFTWARE_RELEASE`), like
the installation bootstrap; later migrations extend the catalogue the same way.

**Scope of a check.** Grants and qualification requirements both fail closed on a dimension the
request leaves empty: a grant limited to a site does not cover it, and a requirement limited to a site
applies to it (`iam.requirement_applies`; a request without a site may be work at that site, INV-26,
IN-04). A request that names another site is outside the requirement. An object with its own site (and product) is checked in that scope (site
values, batch numbers). Installation-wide objects (rule tables, policies, the record register,
retention, incident handling, DI investigations, restores, attestations) are checked in the empty
scope `{}`, which only a grant not limited to a site, area or product covers. Point-of-work actions
(raising or linking an incident, recording a rule evaluation, pinning policies at batch issue,
reserving number ceilings) and every platform permission are checked at the actor's location:
`iam.actor_location_scope()` returns `{site, area}` from the command's session (site and room the
server took from the enrolled device, never from the client), or `{}` without a session (fail closed).

**Order.** A gated function runs its own no-actor and person-only checks (and, where the scope
depends on the object, reads the object), then `iam.assert_not_administrator()` for GMP data
(DI-18), then `iam.require_permission` (DI-17), and only then validates the rest and writes. A refused check rolls the command back; `withGuardedCommand` stores the refusal again.

**Platform AUTHORITY adapter.** `iam.platform_authority(permission, actor, aggregate_type,
aggregate_id)` is registered with `platform.register_hook('AUTHORITY', ...)` (0710). It accepts only
the validated actor of the command (otherwise `EBMR-IAM-002`/`EBMR-IAM-043` as the reason), maps the
platform's lower-case names to catalogue codes (`iam.platform_permission_code`: first segment, a dot,
the remaining segments joined by underscores, all upper case: `platform.settings.change` ->
`PLATFORM.SETTINGS_CHANGE`, `sample_record.submit` -> `SAMPLE_RECORD.SUBMIT`), and evaluates it with
`iam.evaluate_authority` for the actor's person and account in the declared role, at the database
clock, at the actor's location (the platform passes no object scope). Every evaluation is stored
(INV-26). NULL means allowed. An actor it cannot trust or a name it cannot map is returned as the
reason; a denied evaluation is raised as the platform's refusal (`EBMR-PLAT-006 permission <name>
denied: ...`, naming the role, permission, scope, aggregate, reasons and the evaluation id) with the
same JSON DETAIL as `EBMR-IAM-040`, so `withGuardedCommand` stores the failed check again outside the
rolled-back command (DI-17). The platform tests install stub hooks over it.

**Signature types.** `0720_authorization_signatures.sql` gives the approval signature types of the
records and continuity modules the approving permissions (`RECORD_TYPE_APPROVED` ->
`RECORD.TYPE_APPROVE`, `RECORD_DISPOSAL_APPROVED` -> `RECORD.DISPOSAL_APPROVE`,
`DI_INVESTIGATION_CLOSED` -> `DI_INVESTIGATION.APPROVE_CLOSURE`, new vendor type `RESTORE_APPROVED` ->
`CONTINUITY.RESTORE_APPROVE`), so a person signs only what they may approve (esig evaluates the
permission at signing, INV-26).

## kernel.validate_actor_context (migration 0190)

Replaces the shape-only hook. A command is refused unless the account exists, belongs to the
person, is ACTIVE and not locked, the person is ACTIVE, the account is personal (generic and
display accounts can never start a command), the source matches the account kind (SYSTEM and
INTEGRATION only for service accounts), a break-glass account is inside its approved window, the
account holds `role_code` now, `legal_name` (if given) is the current legal name, and the session
exists, belongs to the account, has not ended, expired or locked, runs on an ACTIVE device and is
the device named in the context. On SHARED and GRADE_A_B devices `auth_event_id` must name an
authentication event of the same person and account, made on that device for a command or
signature, within the device class's freshness window (default 60 s), used by no other command
(same correlation ID and same transaction); the command consumes it (INV-40). The session's last
activity is touched and the validated context is logged in `iam.command_log`, so
`iam.assert_validated_actor()` can tell it from a context set by other means.

**Sessions and the sweeps (DI-19, DI-20).** A lockout, a suspension, a deactivation, a device block or
a relocation ends every session of the account or device it can see. `iam.open_session` takes the
login's account and terminal in share mode before its checks, so such a change either waits until the
login has committed and then ends its session too, or commits first and the login is refused: no
session escapes the sweep and comes back to life when the account is unlocked or the terminal
re-activated. The gate still refuses a locked account (IAM-105) and a blocked device (IAM-115) on its
own, as defence in depth against direct writes.

**Badges (DI-19).** A lost, revoked or replaced badge is de-authorised at once, and so is every
authentication event it made that has not been used yet: `iam.lock_auth_event`, which every consumer
goes through (login, unlock, keep-alive, a command's attribution, a signature, a secret change),
refuses such an event (EBMR-IAM-097). The badge functions take the badge's account before the badge,
as logins and commands take it before consuming an event, so a consumer either finishes before the
badge changes (and the loss or revocation then ends its session) or sees the change.

## Policy values (data; ranges enforced by `iam.set_policy`)

Lockout 3–5 (default 5; consecutive failed login or signing attempts, counted since the last success
that proved a secret: a badge tap never resets the count); kiosk idle lock 60–900 s (default 300); personal idle 60–3600 s (900);
absolute session 1–24 h (12 h); attribution freshness per shop-floor class 1–300 s (60);
authentication event max age 10–600 s (120); password length ≥ 8 (12), aging 0–365 days (90; 0
needs compromised-password screening), history 0–24 (5), PIN length 4–12 (6); initial secret
validity 1–720 h (72); badge test interval 30–730 days (365); recertification 3–12 months (6);
alert acknowledgement deadline 1 s–24 h (900 s); break-glass window 5–240 min (60); mirror
staleness 60 s–7 days (1 day); US certification mode BLOCK/FLAG (BLOCK). No regulation sets these
numbers; they are design defaults. The training gate is always a hard block (every site is
India-licensed, IN-04), so the DI-21 flag-and-review relaxation is not offered.
