# Phase 2: open questions for the owner and QA

Defaults in use today are listed. Status: all DECIDED by default (owner decision 0004, 28 September 2026); the owner or QA may still change any of them later.

## Calculations and rounding (expression language)

| # | Question | Default in the build |
|---|---|---|
| E1 | Ph. Eur. rounding counts significant figures per bound, so 0.96 against "not less than 1.0" fails under Ph. Eur. but passes under USP (rounded to the limit's decimals). QA to confirm against the official pharmacopoeia texts. | As described; each parameter names its rule set. |
| E2 | A USP limit with two bounds written to different decimals (e.g. 95.0-105) | The finer of the two decimal places is used for both. |
| E3 | Temperatures | `K` always means a temperature difference; absolute temperatures only in `Cel` or `[degF]`. |
| E4 | `kp` (kilopond) on hardness | Accepted as kgf with an information note; `kg/cm²` only through the controlled legacy alias with a justification. |
| E5 | Nested calculations | Each nested library result is kept at 34 significant digits before the outer formula uses it (no intermediate rounding to reporting precision). |
| E6 | Empty series | `sum`/`mean` of an empty series is an error; `count` of an empty series is 0. |
| E7 | Microbial and potency units | CFU and IU convert only within the same unit; there is no endotoxin unit yet (UCUM's [EU] is a different unit) - deferred with injectables. |

### Kernel items found while adapting Phase 2 to the Phase 1 exit (for the owner and the kernel lead)

Phase 2 does not change the kernel; each item says what Phase 2 does in the meantime.

| # | Kernel item | What Phase 2 does meanwhile |
|---|---|---|
| K1 | **The site policy `site.zone` takes any text (DI-27).** `iam.set_policy` (kernel 0130) checks only whole-number, true/false and listed-value keys, so `site.zone` accepts an abbreviation such as `IST`, a bare offset or a typo. EBMR-IAM-118 (0190) and EBMR-ESIG-035 (0230) then only compare the context's zone with that text, so they accept contexts that declare the same text. Further down the kernel treats the value in different ways: platform entries refuse it (`platform.entry_site_zone`, EBMR-PLAT-017) and so do retention schedules (EBMR-REC-020). But the signature row's UTC offset (`esig.utc_offset`, set by `esig.signature_guard` in 0220; the manifestation's local signing time is derived from it) and the market publication date (0340, `clock_timestamp() at time zone ...`) read the text as a PostgreSQL time-zone abbreviation. In PostgreSQL's default abbreviation set, `IST` is +02:00 (Israel), not India's +05:30 (checked on the development server). On any signature path that does not also go through `platform.entry_site_zone`, a manifestation could therefore show the wrong local signing time labelled IST. The market's "today" would also be a day behind from 18:30 to 22:00 UTC each day. Proposal: a kernel migration that makes `iam.set_policy` refuse a `site.zone` value that `platform.is_valid_time_zone` refuses (an IANA Area/Location name or UTC that the database knows), tested with `IST`, a bare offset and an unknown name. | The server reads `site.zone` at start-up and refuses to start (ConfigError) when the value is not an IANA zone name. It uses the kernel's `time.isValidTimeZone`, which applies the same rule as EBMR-PLAT-017. If the policy changes while the server runs, the server latches SITE_ZONE_CHANGED until a restart: every API and gateway-listener request gets 503, open live displays end, the sweeper stops and one operations alert is raised; the restart then refuses the bad value. Test: `apps/tablets-server/test/platform/startup.test.ts`, "[DI-27] the server refuses to start when EBMR_SITE_ZONE differs from the site policy site.zone, or the policy holds no IANA zone name". Source: the merge review of phase-2/recipe-core (28 September 2026). PROGRESS.md already lists this as a Phase 1 exit follow-up. |
| K2 | **The kernel cannot tell a signing attempt's own committed use of its authentication event from another command's (DI-19).** When a refused signing is logged with its event (`esig.record_signing_failure`, 0230), `esig.signing_misuse` treats any committed use of that event other than the signature as re-use (EBMR-IAM-091). It assumes that a failed attempt's own uses rolled back with it. But the kernel lets a SIGNATURE event attribute the command it is used in (`iam.use_auth_event_for_command` and `iam.consume_auth_event`, 0160). And the Phase 2 plan (section 6) commits a refusal before signing on purpose: the refused COMMAND row, which on a kiosk must carry the event that command consumed (INV-40). If that refusal were logged with its event after the commit, the kernel would raise a HIGH alert against the rightful signer. Leaving the event out, as the previous round did, skips the kernel's checks for re-use, an event made for another challenge or before the challenge, and missing components. Proposal: let `esig.record_signing_failure` recognise the attempt's own command. For example, called inside the attempt's transaction, it could disregard a use with `xact_id = pg_current_xact_id()`; or it could take the attempt's correlation id and disregard a COMMAND use that carries it. Test it with a refused attempt, a real re-use and a replay. | Every refusal before signing is logged with its event while no committed row uses the event. The attempt's command rolls back. The failure is then logged with the event, so the kernel runs all its attempted-misuse checks. Then a second command, attributed by the same event, runs the handler's dry run again, commits the refusal record and stores the answer under the idempotency key; it never signs. A resend of a stored refusal also rolls back and is logged with its own event (`beforeReplay` in `platform/db/commands.ts`). The cost: on a refusal the dry run runs twice. If the record changes between the two runs, the refusal record is what the handler finds on the second run; the refusal logged and answered is the first. With the proposal, the ceremony could go back to one command. Code: `apps/tablets-server/src/features/esig/index.ts`. Tests: `apps/tablets-server/test/esig/ceremony.test.ts`, "[INV-10] a dry-run refusal creates no signature ...", "[DI-37][INV-10] a record changed after the challenge answers CONTENT_CHANGED ..." and "[DI-19][INV-10] a refusal before signing and its resend are each logged with their own authentication ...". Source: the round-3 merge verification of phase-2/recipe-core (28 September 2026). |

Status: DECIDED BY DEFAULT (decision 0004), 30 September 2026. Source: the round-4 verification of the Phase 2 review
fixes. With the application's database credentials alone, a writer held the room's advisory lock and cancelled the
gateway listener's heartbeats queued behind it, so a working scale read OFFLINE for want of heartbeats and a weight
keyed by hand through the honest server was accepted beside it; X11 and X12 were reproduced as well. Tablets 0350 and
kernel 0970 close those levers. Each default is the stricter choice; X11 and X12 are replaced by X19 and X18. The owner
can direct another route.

| # | Question | Default in the build |
|---|---|---|
| X15 | How are a room's heartbeats and its hand-keyed weighings kept apart, now that any role can take an advisory lock? | With rows of `tab.scale_room_lock`, a table the application role holds no privilege on, so it can neither take nor hold these locks (tablets 0350). The database's own functions take a room's row exclusively before a write that can turn a scale ONLINE (a heartbeat, the API reachable again, a reading after a refusal); the gate takes it in share mode and never waits (EBMR-EXE-074, "reporting its status"). The advisory lock `tab.scale_room:<room>` is no longer used. Two hand-keyed weighings in one room still pass the gate at the same time. |
| X16 | May an application process cancel or end another connection's work? | No; only a superuser may (kernel 0970). `sandbox.apply_connect_policy()`, which provisioning, the test harness and the restore procedure run, takes `pg_cancel_backend` and `pg_terminate_backend` away from PUBLIC and from every role that is not a superuser, and the migration fails if that did not take effect. A copy made from a template keeps it. While a database has lost the policy (`kernel.backend_signals_restricted()` is false: a grant made by hand, a restore run without a superuser, a login role put in `pg_signal_backend`), the gate refuses every weight keyed by hand (EBMR-EXE-074). | X17 | Does a missing heartbeat prove that a scale cannot be used? | Only when no heartbeat of its gateway that names the scale was received in the 10 seconds before the weighing's transaction began (or since). The receipts and the heartbeats' commands run on pools of their own, apart from the browser routes' pool (X30), and every heartbeat is answered within 3 seconds whatever holds up its command (X29), so a heartbeat held up (its session's row or its room's row held), cut off or refused keeps the manual path shut instead of opening it (EBMR-EXE-074, "were not recorded"). A receipt written by someone else can only keep the path shut, and the application role would need the gateway's token hash, which it cannot read (since follow-up round 4 it may not write one at all, X36). | X44 | Which clock do the lifetimes of the tickets the server keeps in memory run on? | Both of the process's clocks, and the earlier lapse wins. The answer therefore comes at most 5 s after the reading is journalled, as before this follow-up, within the 20 s the server's capture request allows when it names no stability timeout (the gateway's default stability timeout is 10 s, and the 10 s beyond it also cover the last commands to the balance and the journal write). A first version of this fix waited for the write without a bound, so a disk stalled for some seconds could push the answer past that limit and make the server record a working gateway's API as unreachable (SCALE_OFFLINE; the manual path may open). When the uplink stops, an acknowledged capture is answered true at once and any other false. The server does not rely on `uplinked`: it returns a reading only once its own row exists (READING_NOT_RECEIVED otherwise). The owner may instead require the watermark on disk before any answer; that answer then has no bound on a stalled disk. |
| X33 | What becomes of a change to the acknowledgement watermark that rests on what the server said before a login, when its turn at the journal comes after that login's adoption of the server's head (a write that waited behind a hung one, an upload's or a heartbeat's answer that was on its way)? | It is dropped: nothing is written, it is not a failure and nothing is alarmed for it; the login's head stands. The journal counts each adoption a login asks for, when it is asked, and every other watermark change names the basis it was asked on (the chain, and that count when the request to the server went out: an upload's with its batch, a heartbeat's before it is sent). An answer that arrives once its basis is no longer the journal's is dropped on arrival: it is not kept in memory as what the server holds (the next batch starts after the login's head), not written, and no waiting capture is told by it (the capture is told when the reading sent again is acknowledged, or answers false when its 5 s end). A write asked for earlier that is still waiting is checked again under the journal lock, where it is made, and is STALE there. A dropped write clears nothing either: a watermark failure recorded before it stands until a write succeeds or a login's adoption of the server's head is written (a login whose adoption cannot be written fails and resets nothing, so the scale stays not ready). Only a login's adoption may switch the chain. So after a re-enrolment a write for the old chain never fails on the new one (the gateway stayed NOT_READY until the next login, with a false ACK_WRITE_FAILED) and never switches the journal back to the old chain; an upload's answer is recorded against its batch's chain, never the one current when it arrives (the new chain's reading of the same number was taken as delivered); and on the same chain a stale acknowledgement never moves the watermark, on disk or in memory, past a login's head after the server was restored from a backup (the readings after it were not sent again, or the next reading was sent out of sequence and refused). The stricter side is taken where the order is unclear: an answer that arrives after a login's adoption was asked for but rests on an earlier basis is dropped even if it is newer than the login's head, so the readings after that head are offered again (the server answers DUPLICATE for those it holds, by reading id). A heartbeat's answer that shows fewer readings than acknowledged still raises its UPLINK_FAILED alarm (what the server answered) when it is then dropped. The owner may instead want a dropped change alarmed. |
