Batchwright: a dynamic library of tablet blocks

Assessment and plan for the owner · 1 November 2026 · approved by the owner on 1 November (decision 0026) · revised the same day with the plan review's additions, still 11 slices · slices C (R11) and D (R12) are paused

In short

  • Why new tablets need code today: every process step is written as a TypeScript program. There are 24 tablet blocks (about 9,300 lines), 10 generic blocks (about 4,500 lines), around 38 database files that check the same rules again for each block, and a screen layout for each block. The software only knows how to run a step if someone has written code for it.
  • Fix: turn a block into a form defined as data. It is built from about 14 field types, and only those field types are code, written once. QA approves library items and formulations. Batches are generated from the formulation. One generic screen shows every block.
  • What stays: the compliance core you already paid for: the engine, audit trail, e-signatures, the master record life cycle, execution, review, release, materials and formula, equipment and cleaning.
  • Freeze, not delete: injectables, the site gateway, simulators, analytics, integrations and the other extras. Their code and tests stay in the repo, but no new work goes into them.
  • Review (1 November): approved with additions, now folded in. Calculations can read values from outside the step (formula line, batch size, lot assay, earlier steps). Fields can be conditional. The formulation pins each block's version and content hash. A limit looser than the registered specification is still refused. There is one new decision (O-9), and O-7 needs your explicit answer.
  • Size: 11 slices. Slice 11 is the acceptance test: three very different tablets set up on screen with no code changes. Eight owner decisions are listed in section 6, and one of them changes how DI-04 is implemented.

1. Diagnosis: why a new tablet needs a software session

The master record (MBR) format itself is data. Parameters, limits, units and stages are already stored as data. The trouble is that each step in it refers to a block type, and a block type is a program. The approved outline wanted it that way (outline 6.6: "a block type is vendor code; customers cannot create primitive types"). Anything a product needs that a block's program does not already offer means writing new code.

Where the code sits

  • Block programs: apps/tablets-server/src/blocks/tb-01.ts … tb-24.ts. Each file holds a config schema, entry kinds, a handler and exception rules (160 to 816 lines each). They are registered in code in features/edition-blocks.ts.
  • Database copies of the rules: for example 0873_compression_blocks, 0891_ipc_calculations and 0910–0912 for coating. A new rule therefore has to be written twice, once in TypeScript and once in SQL.
  • Screens: BLOCK_LAYOUTS in floor/renderers/tablets.tsx lists each block version by hand, and so does TABLET_ENTRY_KINDS_BY_BLOCK in api-contract/src/tablet-entries.ts.
  • Pharmacopoeia limits: they are TypeScript constants (RULE_SETS and PROCEDURE_KEYS in blocks/ipc/rule-sets.ts). A new test method or a new market needs code.
  • Lists in a step's settings cannot be edited on screen: "Lists and maps are shown read-only" (designer/components/ConfigForm.tsx). That covers IPC schedules, coating phases and sampling plans.
  • Product set-up: the validator refuses any block that is not registered in code (FLOW-BLOCKS, ENG-DEF-BLOCK). Every demo and golden product so far was written as JSON or TypeScript in the repo (templates/gb-t-01.mbr.json is 3,477 lines, plus cli/demo-route-masters*.ts and cli/demo-p3.ts), not on screen.

4. Target design

4.1 Field types (the only part that stays code)

A library block is a form. It is built from these field types, each written once with tests:

Field typeWhat it records and checks
NumberValue, unit, decimals. Limits are filled in by the formulation: target, alert and action, registered. Out of limit raises an exception, and a registered breach also raises a deviation flag (PR-08).
TextFree text with an optional pattern (e.g. a punch ID)
Yes / NoWith the expected answer. An unexpected answer raises an exception.
ChoiceFrom a list, with optional "not allowed" choices
Date / timeTrusted-time stamp
TimerStart and stop, with a minimum or maximum duration (mixing time, drying time, hold time; PR-30)
WeighingBalance, gross, tare and net, material lot, BOM line, two-person check when keyed by hand. Uses the existing weighing and lot-status code.
Material lotScan a lot, check its status and expiry and that it was dispensed to this batch
Equipment / roomPick equipment of the class the formulation set, and check its clean, calibrated and in-use status. It also books the equipment or room, which closes gaps A2–A4.
ContainerRegister or consume an output container (genealogy)
SampleUnits taken, purpose, sample label
Test resultn replicates, giving mean, min, max and RSD, each against its own limits. Time points cover dissolution, and stages cover acid then buffer.
CalculatedAn expr formula over other fields: yield, reconciliation, weight gain %, mean. It cannot be typed by hand (INV-25).
SignatureMeaning (performed, checked, verified, QA) and role, with the two-person rule

Values from outside the step. A calculation can read four kinds of value: the scaled quantity of a formula line, the batch size, the approved assay of the lot being weighed, and a value from an earlier step (such as the LOD or the granule yield). The formulation says which line or step. This covers potency-adjusted dispensing (today's TB-01) with no code.

Conditional fields. A field can be shown only when an earlier yes/no or choice field has a given answer. Examples are rework fields when "rework added" is yes, or a peel test only for a peel-off blister. A calculation may read a conditional field only under the same condition.

The fields are arranged with two pieces of structure. Sections group fields. Repeat groups add rows per container, per time interval, or "until within limits", which covers the LOD drying loop, coating weight-gain checks and IPC rounds every 30 minutes.

4.2 Block definition (data)

{ code: "IPC-FRIAB", version: 3, title: "Friability", category: "TEST_IPC",
  sections: [{ title: "Run", fields: [
    { id: "units", type: "NUMBER", unit: "1", limitSlot: "units" },
    { id: "w0", type: "NUMBER", unit: "g" }, { id: "w1", type: "NUMBER", unit: "g" },
    { id: "loss", type: "CALC", expr: "(w0 - w1) / w0 * 100 [%]", unit: "%", limitSlot: "loss" },
    { id: "cracked", type: "YES_NO", expected: false } ]}],
  frequencySlot: true,
  signatures: [{ meaning: "PERFORMED", role: "IPC_OPERATOR" }],
  referenceLimits: { loss: { max: "1.0", note: "common compendial value; shown as a guide" } } }

The definition says what is recorded. Product values (the limits, units count, frequency and method) go in "slots" that the formulation fills. Each version is stored with a content hash, is audited, and moves DRAFT → APPROVED (QA e-signature) → RETIRED. One generic handler runs every definition inside the existing engine. It checks types, required fields, limits, calculations and signatures, and raises exceptions from the existing list. The registry loads approved definitions as LIB:code@version, so the guard "an MBR never runs on a block the system cannot execute" stays true. One generic database function checks entered values against the formulation's limits and required signatures. It replaces per-block SQL for every library block (decision 0008 §2: database enforcement for the regulation-required core).

4.3 Library seed (ready-made catalogue, about 75 items, all data)

Process (24)

Dispensing (gravimetric, potency-adjusted, liquid), sifting, milling (screen and cone), dry mixing, binder preparation, wet granulation (RMG, FBG), drying (FBD, tray, with LOD loop), sizing, roller compaction, blending, lubrication, geometric dilution, compression (single, bilayer, trilayer), de-dusting, metal detection, tablet printing, rework addition, hold, transfer

Coating (8)

Suspension preparation, seal coat, film coat (IR), functional / enteric coat, top coat, sugar coat phases (sub-coat, smoothing, colour, polish), polishing, coated-tablet inspection

Tests (25)

IPC: average weight, individual weight, hardness, thickness, diameter, friability, DT (water, acid then buffer), LOD, blend uniformity, bulk/tap density, sieve analysis, appearance, weight gain %. Release: assay, dissolution (single, profile, two-stage), content uniformity, uniformity of mass, related substances, water (KF), microbial limits, identification, residual solvents

Controls (11)

Line clearance (start, end), room status, equipment status and cleaning, balance daily check, sampling, yield, reconciliation (material, printed packaging), stage sign-off, deviation reference, QA verification

Packaging (8)

Blister (thermoform, cold-form, peel-off), strip, bottle, cartoning, coding / overprint check, leak test, label reconciliation, shipper

Materials and equipment

Materials, products and equipment classes are already master data. The seed adds common excipients and equipment classes (RMG, FBD, FBP, blender, press, coater, blister machine).

The seed is shipped as data files and loads through the same DRAFT → APPROVED path. QA approves what the site wants to use, and nothing is approved by default.

4.4 Formulation (master record) assembly and approval

  1. Product and formula: materials, per-unit quantity, overages, potency adjustment. This screen already exists (R4).
  2. Process: add stages, drop library blocks into each stage, and fill each block's slots (limits, frequencies, methods, equipment class, hold times). Every list can be edited on screen.
  3. Specifications: IPC tests are blocks, release tests are the existing specifications.
  4. Batch sizes: list the sizes. The system scales the BOM for each one, and all of them are approved together (IN-13 stays as it is).
  5. Sanity checks only: required slots filled, lower limit < upper limit, target inside the limits, units compatible, BOM adds up, every CPP and IPC has limits (PR-03), only approved library versions used. A limit looser than the product's registered specification for a market is still refused (PR-08). A limit looser than the library's reference limit gives a warning that needs a written reason.
  6. On approval, the formulation pins each block's library version and its content hash. A new block version means a new formulation version.
  7. Preparer signs, an independent checker signs, QA approves (PR-02). It becomes effective with its change record (DI-04 per O-2).

4.5 Batch generation and execution

Issuing a batch picks an approved size. The system creates the record with the scaled quantities. The batch inherits the block versions and hashes the formulation pinned, so later library changes do not touch it. The kiosk step screen, the review screen and the printed copy are each one generic renderer that draws any definition: fields by type, limits shown beside each field, an out-of-limit warning as the value is typed, and the signature bar. The per-block layout tables go.

Simplicity review

  • Left out on purpose: a rules engine for "valid combinations", a drag-and-drop form designer (the table editor is enough), scripting beyond the existing calculation language, per-block SQL, per-block simulators, and free batch-size ranges.
  • The one real risk: the "smart" field types (weighing, equipment, container) could grow into block programs again. The rule is that a new field type needs your approval, and it must be useful to at least three blocks.
  • What we lose: a few clever block-specific checks (screen integrity, ribbon checks). They come back as Yes/No and Number fields with expected values and limits. The record gets simpler, and no control is dropped.
  • Size: the new code is roughly field types, one handler, one renderer and one builder screen. About 24 block programs stop growing, and the catalogue grows as data.
