## A1 deliverables

**Scale contract**
- ScaleReading: readingId, gatewayCode, deviceCode, serial, seq, value (decimal string), unit, stable, status OK|UNSTABLE|OVERLOAD|UNDERLOAD|OFFLINE|ERROR, raw, sourceTimeUs, trust DEVICE_SYNCED|DEVICE_UNSYNCED, installation, prevHash, hash, signature.
- Capture request and response; error classes DEVICE_OFFLINE, NOT_STABLE_WITHIN_TIMEOUT, OVERLOAD, UNIT_MISMATCH, SERIAL_MISMATCH, PROTOCOL_ERROR.
- MT-SICS codec.

**Simulator**
- TCP 127.0.0.1:4001 with S, SI, T, Z, I4, @, and responses `S S`, `S D`, `S I`, `S +/-`, `ES`.
- A seeded load model with settle time, noise at resolution d, capacity, tare and zero; an injectable clock.
- Faults OFFLINE, UNSTABLE, OVERLOAD, SLOW, GARBLED, SERIAL_MISMATCH, DRIFT.
- A control API and plain-HTML console on :4002: place container, +0.5 kg, +5 g, remove, faults.
- No third-party dependencies.

**Gateway** (Fastify on 127.0.0.1:3021)
- Config: devices with driver `mt-sics`, host, port, expected serial, resolution.
- The MT-SICS client with timeouts, reconnect back-off and line framing, keeping the raw line.
- I4 serial checked at every connect: a mismatch is refused and alarmed (DI-20).
- SI at 4 Hz for the live SSE; stable capture with a timeout.
- An fsync'd JSONL journal with a hash chain, verified at start, and an ack watermark. Only a login's adoption of the server's chain and head may switch the chain. Every other watermark change names the basis it was asked on (the chain, and the adoptions logins had asked for when the request went out) and is dropped once a login has asked for an adoption since: an answer arriving after that is not kept in memory, written or told to a waiting capture, and a write already waiting for the journal's lock is dropped under that lock, so a write that waited behind a hung one never overtakes the login's head; a dropped write is not a failure and does not clear one (decision X33).
- A capture answers with its reading and whether the server acknowledged it within 5 s of its journalling (`uplinked`, `CAPTURE_ACK_WAIT_MS`): an upload's answer, or the head of a new login that covers it, of the same chain. No upload waits for the ack watermark write (what the server holds is kept in memory), so a reading queued behind another one is not held up by the gateway's disk; the capture answers once the watermark write has finished, but never later than its 5 s, so a slow disk neither turns an acknowledged reading into `uplinked: false` nor holds the answer past the server's request (decision X28).
- Ed25519 signatures with the DEMO-ONLY key.
- A heartbeat every 5 s. While a new login gets no answer (the server can hold it up in its database), heartbeats go on with the last login's token, which the server still receives; a login the server refuses, or that fails in the gateway, stops them (decision X31).
- Uplink: a SERVICE_KEY login at the sandbox server's gateway listener (127.0.0.1:3012) with a key proof, then `POST /gw/v1/readings` (idempotent by readingId, back-off) and `/gw/v1/heartbeat`. Each upload first takes `POST /gw/v1/challenge`, a challenge the database issues; each reading's wait at the gateway is measured after it arrives and signed with the gateway key over the challenge and the reading id (review finding P53, tablets 0330).
- API for the server (bearer service key): `/v1/health`, `POST /v1/devices/:code/capture`, `GET /v1/devices/:code/live` (SSE).
- The only clock read is in `clock.ts`. Readings carry the installation kind; time trust is DEVICE_UNSYNCED unless sync is reported.

**Server**
- The gateway listener:
  - `identity.authenticate(SERVICE_KEY)` with the gateway device fingerprint, then `openSession`;
  - an opaque bearer token;
  - `tab.ingest_reading` in an INTEGRATION command (INTERFACE.WRITE), after the Ed25519 signature is verified against `tab.gateway_key`;
  - installation kind must match; seq continuity is enforced;
  - integration identities can never sign.
- Browser `POST /api/devices/scales/:code/capture {purpose}`: a trigger, not a user GMP write. The server calls the gateway, which journals and uplinks the reading; the server returns a ReadingView after the row exists.
- `GET /api/devices/scales?room`; `GET /api/devices/scales/:code/live`, an SSE relay that is display-only.
- Heartbeat gap over 10 s → OFFLINE status, shown in the StepScreenView header via the port.
- Whether the server reaches each gateway's API (a capture that cannot reach it, and a probe of `/v1/health` on each heartbeat while it is marked unreachable) is recorded in a command of the server's own gateway API monitor identity: a SERVICE account in the role GATEWAY_API_MONITOR, which holds GATEWAY.API_CONTACT_RECORD and nothing else (sandbox: TEST-gw-monitor on TEST-SRV-MONITOR, from the service-keys file; tablets 0340). The database takes the report from nobody else and audits each change of state under that identity.
- A weight keyed by hand beside a scale whose heartbeat says ONLINE is accepted only on a report that the scale cannot be used (API unreachable, a refused reading of the chain) written before the weighing's transaction and standing for 10 s; a heartbeat written in the weighing's own transaction refuses it. The database records with each hand-keyed weighing the status and reason of every scale of the room it counted (`tab.manual_weighing_basis`; tablets 0340, review P50/P51 round 3).
- A holder of the application role's database credentials can no longer make a working scale count as unusable, and so open the manual path beside it, by holding its room's lock, by cancelling, ending or holding up the listener's heartbeats or their commands, by a heartbeat of its own that says OFFLINE, by a report held uncommitted, by reading an old snapshot, or by keeping the listener from putting what it receives on record (loading the database, taking its connections) (tablets 0350, kernel 0970 and 0980; review P50 round 4 and follow-up rounds 2 to 4; decisions X15-X21, X29-X32, X36-X42). What such a holder can still do is deny the fallback (keep the manual path shut), never open it beside a working scale:
  - the listener logs in with a role of its own (`ebmr_listener`, in a sandbox `ebmr_sandbox_listener`; `EBMR_DB_LISTENER_URL`; kernel 0980), which alone may write receipts, answers of the gateway's API and the listener's ticks; that role is limited to the listener's share of the connections (8 for one listener) and the application roles' connection limits keep that share free for it, and it opens its receipts pool (4) and its watch's connection (1) before it listens, opening a lost one again at once (decisions X36, X38, X41);
  - the gate fails closed: every 500 ms the listener ticks on its own connection, saying whether everything it received since its previous tick was put on record (a receipt or an answer that failed or never ran, or a heartbeat refused before its receipt, makes the tick unclean); the gate counts a scale silent, never reported, recorded not ONLINE, or its API report unanswered only over a window the listener vouched for (its latest closed tick at most 2 s old, clean ticks without a gap over a full 10 s, no second listener ticking or ending in it, no other run that stopped without being ended within the last hour, and no run of another run key, or of none, that closed a tick within the last hour), and otherwise refuses (EBMR-EXE-074, UNATTESTED). The basis records where the vouched window started (decision X37). When the server closes, the listener ends its run on record (`tab.end_listener_run`); a run that stopped without being ended (a killed server, or a holder of the listener's credentials keeping the real listener's ticks from landing while it ticks a run of its own) keeps every other run from vouching for an hour after its last tick (decision X40). The listener's login may set session defaults on itself, which would reach the listener's next connections: nothing is vouched for while such a default stands, and the listener's pools fix the settings that would keep its statements from landing (read-only transactions, idle timeouts) in their startup options (decision X42). Each run begins on record before its first tick with a run key derived from the server's secrets (`EBMR_SECRETS_FILE`; the database keeps its SHA-256, `tab.begin_listener_run`): the server started again with the same secrets vouches as before, while a run of another key, or of none (someone holding only the listener's credentials, with no listener running), vouches for nothing until an hour after the last tick of a run of the server's key; a run held so is logged at warn as it begins (decision X43);
  - the listener puts every heartbeat on record as received (`tab.record_heartbeat_receipt`, outside any command, no lock another transaction can hold) before its command, in one statement on the receipts pool that also reads the session behind the token and the site's time zone (a wait for a connection ends after 1 s, a statement after 2 s; a receipt not written within them fails the request and leaves the listener's tick unclean); a missing heartbeat counts only when no heartbeat naming the scale was received in the window;
  - every heartbeat is answered within 3 s of its arrival, below the gateway's 5 s interval (503 `HEARTBEAT_PENDING` while its command, one per gateway at a time on the reports pool, goes on in the background), and so is a gateway that must log in again after a restart. The reports pool's 4 s limit bounds each wait for a connection and each statement, not a command as a whole; the answer's deadline is what keeps the gateway's next heartbeat on its interval, so two receipts are at most about 8 s apart as long as each is written within its limits. Only tokens this process handed out use the receipts pool freely; any other token takes its turn, one at a time, and other gateway requests check the zone on the application pool (decisions X29-X31);
  - a state that is not ONLINE counts only once it has been recorded for 10 s with no heartbeat received since saying ONLINE (`offline_since`), so the manual path opens 10 s after a disconnect;
  - the API report counts from when another transaction first saw it (`seen_at`) and only while the API has not answered the server since; the server records every answer to its probes on its own (`tab.record_gateway_api_answer`, receipts pool) before the monitor's command, and a probe never waits for that command (held up, it only delays the next observation, one at a time). An answer not recorded within the receipts pool's limits is lost, logged at warn with the gateway code, and leaves the listener's tick unclean, so the report does not count meanwhile (decisions X32, X37);
  - heartbeats and the gate lock rows of the owner-only `tab.scale_room_lock` (no advisory lock); no role but a superuser may cancel or end another connection (`sandbox.apply_connect_policy`), and the gate refuses while that policy is lost (`kernel.backend_signals_restricted()`) or outside READ COMMITTED;
  - still open (decisions X31, X39): a database under enough load that a receipt's or an answer's statement runs past its 2 s, or the listener's ticks stopped, keeps the manual path shut beside the gateway's scales (a denial of the fallback, never a weight beside a working scale); so does a listener that has just started, for 10 s. Two listeners ticking on one database vouch for nothing, and a run that stopped without being ended holds the others for an hour (unless the scale is taken out of service in the registry). The listener's share is a hard limit: past its 3 spare connections (backends a network fault left half-open still count) or in a deploy whose old and new servers overlap under one listener's share, the listener cannot open its 5 connections and fails closed (a lost connection not opened again, logged at warn, and nothing vouched for over what it could not record; or the server refuses to start); a cluster that deploys with overlap declares 16 (X41). A holder of the listener's own credentials can still make the database vouch for a run of its own, once it has ticked clean for 10 s, when no run of the server's run key has ticked for over an hour (X39 (6), X43): because no listener ran for that long (none ever ran on the database, or the server runs without `EBMR_GATEWAY_LISTEN` or stays down), or because the holder keeps the real listener out for the hour, by load or the role's slots kept up for the hour, or by changing the role's password before the listener's next reconnection or restart, which the database cannot bound (an alarm on the listener's warnings, the server's run key registered by the operator, and a credential bound to the server's host are the owner's routes). Until X43 no hour was needed after the listener's run ended on record (a planned restart or deploy) or on a server that never ran one. A holder of the server's secrets as well needs no hour. After a change of the server's secrets, or a development server started again without a secrets file, the manual path stays shut beside the gateway's scales for an hour (X43). After a restart a flood of requests with made-up tokens can hold up the gateway's first heartbeat until its answer is due. While a heartbeat's command is held up the scale shows OFFLINE and its capture is refused, but the manual path stays shut (a denial of both paths, not a weight beside a working scale).
- `deviceReadingPort.claim(client, {readingIds, room, maxAgeUs (policy, 120 s), purpose})`, called inside C3's command. It checks each reading:
  - exists and is stable;
  - comes from an ACTIVE INSTRUMENT registered to the kiosk's room (DI-20);
  - is at most `maxAge` old at database time (its wait before the insert is the gateway's signed wait plus the database's own time since the upload's challenge);
  - has not been used; `tab.reading_use` is inserted.

  It returns `{value, unit, raw, deviceCode, sourceTimeUs, trust}`.
- `seed`: `TEST-BAL-01` instrument and gateway key registration (with the test-kit persona seed).
