# Module brief B3: market-profile engine (kernel)

Schema: `market`. Migrations: packages/kernel/sql/0300_*.sql .. 0399_*.sql. Source: packages/kernel/src/market/. Tests: packages/kernel/test/market/. Rule-table data files: compliance/rule-tables/ (create it). Migration filter: EBMR_MIGRATIONS='^(00|03)'.
Controls: IN-52 (stub scopes). Invariants you own: INV-28, INV-29, INV-47. Also "policy versioning" (outline 3.5).
Read: outline 3.3 (all of it), 3.5, 3.6, 5.8; ADR 0008 and 0014; docs/regulatory/control-catalogs/D-india-schedule-m.md section B (India resolution table B-01..B-26) and the IN-52 control file; docs/decisions/0001-outline-v0.2-decisions.md (Decision 2: no tiered FDA/India APS acceptance in v1).

Build:
1. Rule model as data: keys (atomic: one dimension, one unit, comparison method SMALLER_STRICTER, LARGER_STRICTER, ORDERED with its ordered list, REQUIRED_IF_ANY, SET_UNION, ALL_APPLY, and a NOT_COMPARABLE method that requires a stated method), key namespaces (kernel.*, tablets.*, sterile.*) in separate, separately versioned tables (L-57); rows (key, market IN/US/EU, optional predicate, value, unit, floor type HARD/GUIDANCE/EXAMPLE/DESIGN, source citation, verification status, effective_from, effective_to). Rows are insert-only; a change is a new row plus a new table version (never edit a row in place). Table versions are immutable once published and carry a content hash.
2. Loader: a TS loader that reads versioned YAML/JSON rule-table files from compliance/rule-tables/ and publishes them as a new table version through a SECURITY DEFINER function (with validation: unknown method, unit mismatch, overlapping effective windows for the same key/market/predicate, India missing for a key that India governs -> refused). Seed a first kernel table with real keys drawn from table B where they are kernel keys (retention components B-01, reason-for-change B-21, master-record two-person approval B-20, audit-trail review B-22, release authority B-23, self-inspection B-08, management review B-24) and a starter tablets and sterile table with a few keys each (B-03 compression IPC interval, B-14 weight bands as ALL_APPLY, B-13 particle limits per grade, B-16 HEPA leak-test interval, B-17 filter use, B-10 APS acceptance per Decision 2). Every row cites its source as a paraphrased reference (clause id), not regulation text. Mark unverified values with their verification status.
3. Resolution engine (pure TS, decimals as strings or bigint scaled integers; never JS number for GMP values): resolve(key, marketSet, predicates, asOf, tableVersion) -> {value, unit, governingMarkets, predicateBranch, method, tableVersion, inputs}. India is always added to the market set (INV-28): a market set without IN is refused. For every comparable key, the resolved value is at least as strict as India's (property-based test with fast-check, installed at the repo root).
4. Scopes (stub): PRODUCT/PACK (batch market set), SITE, LINE/ROOM/EQUIPMENT/PERSON as the union of markets of products qualified there, MATERIAL_LOT resolved per consuming batch. Define a `ResolutionContext` port interface the editions will implement; for Phase 1 provide stub scope tables (stub lines, rooms, equipment, lots, product qualifications) in your schema, clearly named stub_*, so tests can exercise union-of-markets scopes.
5. Stored evaluations (INV-29): a SQL function that records every resolution (value, governing market, predicate branch, rule-table version, inputs hash) in an insert-only, audited table; nothing else writes it.
6. Site values: may only tighten. A site value looser than a HARD row is refused; loosening a GUIDANCE or adopted EXAMPLE value needs a CCS reference and QA approval (store the approval ids; the signing module comes later, so accept an approval-record uuid) and is flagged on affected batches. Source corrections are a separate path (citation, two approver ids, new table version) and are not treated as loosening.
7. Policy versioning (outline 3.5 and INV-47): policies/switches as versioned data with effective dates; `policy_for_batch(batch issue instant)` returns the version in force at issue; a loosening policy version never applies to a batch issued before its effective date (bypass test: try to apply it through raw SQL and through the function).
8. Change impact: when a new table version is published, produce an impact list of stub MBR/site-value references whose pinned values are looser than the new resolved value (simple version is fine).
Tests: IN-52 catalog_test lines (with stub scopes), INV-28 property test, INV-29 bypass (app role cannot insert/update evaluation rows directly), INV-47 bypass, ALL_APPLY and SET_UNION behaviour, predicate branch recording (retention with Form 25 vs Form 28 licence predicate), effective-date selection, loosening refusal.
