# Module brief B1: identity and access (kernel)

Schema: `iam`. Migrations: packages/kernel/sql/0100_*.sql .. 0199_*.sql. Source: packages/kernel/src/identity/. Tests: packages/kernel/test/identity/. Migration filter while developing: EBMR_MIGRATIONS='^(00|01)'.
Controls you implement: DI-14, DI-15, DI-16, DI-17, DI-18, DI-19, DI-20, DI-21. Invariants you own: INV-11, INV-26, INV-40 (and the "user IDs never reused" part of INV-27).
Read: outline 4.7 (security), 5.5 (e-signatures and attribution: you build the authentication service and authentication events the signing module B2 will consume; B2 starts after you), 7.1, 7.2, 7.4; docs/design/features-ux-roles-configuration.md (roles list A.2 and anything on accounts, badges, delegation, shared devices); ADR 0006, 0012, 0001 (identity is site data; for Phase 1 build it in the kernel and test in one database; note in your README that edition databases will hold mirrors later).

Build:
1. Persons (verified identity, legal name, identity-verification record: who verified, method, evidence ref, when; DI-15), accounts (kind: HUMAN, SERVICE, INTEGRATION, READONLY_DISPLAY; flag generic/shared; status; login name never reused, even after deactivation: enforce with a permanent register of issued identifiers; accounts are never deleted), at most one active GMP-capable account per person (partial unique index), rehire keeps the same person.
2. Roles and permissions: a role catalogue (seed the kernel roles from the features doc, grouped as master records / execution / quality and release / administration & security) with permission sets; grants of a role to an account for a scope (site, area/room, product) with validity window, granted-by, approved-by (requester is not approver), recorded reason. Point-in-time access list query (who held what at instant T; DI-16), recertification records with due dates, revocation effective immediately (DI-16 test lines).
3. Static segregation refused at grant time: admin role + any GMP role for the same person anywhere in the installation (INV-11, DI-18); write/sign/verify/acknowledge permission on a generic/shared or READONLY_DISPLAY account (DI-14); SERVICE/INTEGRATION accounts can never hold sign permissions. A person's admin account can never act on that person's own GMP account or grants. Enforce with triggers/constraints so that raw SQL through ebmr_app cannot bypass them (bypass tests).
4. Credentials: local password (argon2id via @node-rs/argon2, hashed in TS, verifier stored in DB), badge + PIN (badge UID hashed; badge states ISSUED/ACTIVE/LOST/REVOKED/REPLACED with identity re-verification on replacement), password/PIN policy as data, initial and admin-reset secrets single-use and must be changed before the account can sign (DI-15, 11.200/11.300 paraphrased), lockout after N failed attempts (default 5, allowed 3-5, as a policy value), misuse events (failed logins and signings, use of locked/disabled accounts) written to an alert table with acknowledgement and escalation state (DI-19). Administrators never see secrets.
5. Devices: registry with class (PERSONAL, SHARED, GRADE_A_B, SERVER), room binding for GRADE_A_B, enrolled key fingerprint/certificate thumbprint; the server derives device class and room from the device record, never from client-reported data (DI-20). Blocked/decommissioned devices refused.
6. Sessions: server-side sessions bound to account and device, idle and absolute timeouts as policy values (kiosk lock default 5 min, allowed 1-15), one active shop-floor session per person (a new login ends the old one), lock/unlock.
7. Authentication events: the authentication service (TS, packages/kernel/src/identity/) verifies the required components (password; badge+PIN) and inserts a single-use authentication event bound to person, account, device, optional challenge id (uuid, for B2), components used, and recorded_at. Only a SECURITY DEFINER function inserts them; ebmr_app cannot insert or update them directly. Provide `iam.consume_auth_event(event_id, expected_person, expected_challenge, max_age interval)` that marks it consumed atomically (single use) for B2 and for INV-40.
8. Replace the hook `kernel.validate_actor_context(jsonb)` (create or replace in YOUR migration; it is called by kernel.begin_command) so that a command is refused unless: the account exists, is active, belongs to person_id, holds role_code in scope right now; the session is active, belongs to the account and is not timed out (touch its last activity); for source SYSTEM or INTEGRATION the account is a SERVICE/INTEGRATION account; and, when the session's device class is SHARED or GRADE_A_B, `auth_event_id` refers to an unconsumed-or-this-command authentication event of that same person within the device class's freshness window (default 60 s), which the command consumes (INV-40). Error codes EBMR-IAM-<NNN>. Put this replacement in its own migration file.
9. Qualification register stand-in (INV-26): qualification types, person qualifications with valid-from/to and source, required qualification per role/permission as data; a function `iam.evaluate_authority(person, account, permission, scope, at)` returning allowed/denied with the evaluated inputs, and a table that stores each evaluation (INV-26 "the evaluation is stored"). Freshness bound concept can be a stub column for mirrored data.
10. DI-21: training/acknowledgement records (first-use e-signature accountability acknowledgement; signature register listing each person's signature manifestation name and handwritten-equivalence acknowledgement). An account cannot sign until acknowledged (expose a function B2 will call, e.g. `iam.assert_can_sign(account)`).
11. Delegation table (outline 7.1): delegator, delegate, scope, meanings, window, SOP ref, approved by someone other than the delegate, no re-delegation. Only the data model plus validity check function; B2 uses it.
12. Leaver processing: deactivation ends sessions and grants immediately.
Register every GMP table with kernel.register_audited_table (credentials: store only hashes; audit diffs must never contain secret verifiers: exclude them or store them in a separate non-audited table that is protected and whose changes are audited as metadata only; explain your choice).
Also write `packages/kernel/test/identity/seed.ts` exporting `seedActor(db: TestDatabase, opts?: { roleCode?: string; deviceClass?: string; source?: ...; ... }): Promise<ActorContext>` that creates a person, account, role grant, device and session (and an auth event when the device is shared) through the admin pool or your functions, and returns a valid ActorContext. The lead will use it to switch all modules' tests to real identities. Also export a helper to seed a SERVICE account actor for source SYSTEM.
Write tests for every catalog_test line of DI-14..DI-21 and bypass tests for INV-11, INV-26, INV-40, and account-id non-reuse. Update the existing audit-trail tests? NO: do not edit them; the lead will switch them to seedActor.
