## Conventions
- SQL migrations: plain SQL files in your numeric range, each starting with `set local role ebmr_owner;` after any `create schema` (schemas must be created before `set local role`, with `authorization ebmr_owner`). Objects are owned by ebmr_owner. Functions the app may call are SECURITY DEFINER with `set search_path = pg_catalog, kernel` (or your schema) and get an explicit `grant execute ... to ebmr_app`. The app role gets only the table privileges it truly needs; everything GMP-relevant is written through kernel functions or audited tables. Register GMP tables with `select kernel.register_audited_table(table, aggregate_type, aggregate_column, insert_only)`. Error messages start with a stable code `EBMR-<AREA>-<NNN>`.
- Never edit a migration file after its tests pass in the full suite; add a new file instead (checksums are enforced).
- TypeScript: strict, ESM, `.ts` import suffixes, `import type` for types. No `Date.now()` or argument-less `new Date()` in src (lint enforces); time comes from the database (`clock_timestamp()`), which is authoritative (INV-16). No JavaScript `number` for GMP quantities.
- Tests: Vitest, one database per test file via `createTestDatabase()` from packages/kernel/test/support/db.ts; attack invariants with raw SQL through `db.app` (application role) in "bypass" tests; use `db.admin` only for setup or superuser-level attacks. Every test that proves a control or invariant carries the IDs in the test name, e.g. `it('[DI-14][INV-11] ...')`. Implement at least one test per `catalog_test` line of each of your controls, plus a bypass test for each invariant you own.
- Run only your tests while developing: `EBMR_MIGRATIONS='<your filter>' npx vitest run <your test dir>` (your filter is given in your brief; it applies the foundation plus your migrations). Before finishing also run the whole kernel suite without the filter (`npx vitest run packages/kernel`) and report if another module's in-progress work breaks it (do not fix other modules).
- Typecheck with `npx tsc -p tsconfig.json` and lint with `npx eslint <your paths>`; fix errors in YOUR files only.
- Paraphrase regulations; never copy more than ~10 consecutive words of regulation text into code or docs.
- Write a short `README.md` in your src module folder: purpose, tables/functions, invariants and controls covered, how other modules call it.

## Coordination rules (added by the lead; they override anything above that conflicts)
- **One schema per module.** Put your tables and functions in your own schema (named in your brief), created with `create schema if not exists <name> authorization ebmr_owner; revoke all on schema <name> from public; grant usage on schema <name> to ebmr_app;` before `set local role ebmr_owner`. Functions use `set search_path = pg_catalog, <your schema>, kernel`. The existing `kernel` schema holds only the audit trail; do not add objects to it (except B1, which replaces `kernel.validate_actor_context`).
- **No foreign keys into another module's schema.** Other modules are built at the same time. Reference persons, accounts, sessions, devices and authentication events by `uuid` columns; the actor of a command is `kernel.current_actor()` (jsonb with person_id, account_id, role_code, session_id, device_id, auth_event_id, source, site_zone, correlation_id, reason_code, reason_text). The lead adds cross-module FKs during integration if needed; list any you want in your final message.
- **Actors in tests.** Get every actor context in your tests through ONE helper in your own test folder, e.g. `packages/kernel/test/<module>/helpers.ts: export async function testActor(db: TestDatabase, overrides?: Partial<ActorContext>): Promise<ActorContext>` whose body for now is `return actor(overrides)`. The identity module (B1) will make `kernel.begin_command` refuse unknown persons/accounts/sessions; the lead will then switch every module's `testActor` to seed a real identity. So never build ActorContext objects by hand and never call `actor()` directly outside that helper. If your full-suite run fails only with identity errors (codes EBMR-IAM-*) in your tests, that is expected: report it, do not work around it.
- **Time:** every table that records an event has `recorded_at timestamptz not null default clock_timestamp()` set by the database; application-supplied times go in a separate `occurred_at` with a trust level (see outline 5.6) only where a claimed time is meaningful.
- **Migration file names:** `<4-digit number>_<snake_case>.sql` inside your numeric range only.
- **Docs:** if your brief asks for docs, write them only under the doc paths it names.
