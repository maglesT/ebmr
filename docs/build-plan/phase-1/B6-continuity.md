# Module brief B6: security baseline, backup/restore, restore events, batch-number register

Schemas: `continuity` in the kernel; `site` in site services. Migrations: packages/kernel/sql/0600_*.sql .. 0699_*.sql and packages/site-services/sql/0600_*.sql .. 0699_*.sql (create the folder; site-services migrations run in the same test template DB after the kernel's, namespace 'site-services'). Source: packages/kernel/src/continuity/ and packages/site-services/src/ (you may edit packages/site-services/src/index.ts to export your module; do not edit its package.json: if you need a dependency there, say so; @ebmr/kernel imports from site-services are fine only via the kernel's public API, and the kernel test harness already applies site-services migrations). Tests: packages/kernel/test/continuity/ and packages/site-services/test/. Scripts: ops/ (create it) for drill scripts. Docs: docs/security/ and docs/operations/ (create them). Migration filter: EBMR_MIGRATIONS='^(00|06)'.
Controls: DI-13, DI-45. Invariant you own: INV-27 (never reused numbers after a restore), and the "a signed restore event covers the gap" part of INV-08 (audit anchors vs restore).
Read: outline 4.2 (topology, deployment and continuity), 4.4, 4.7 (security architecture), 5.4 (audit trail, anchors), 7.1; ADR 0001, 0007, 0012; controls DI-13, DI-45, IN-18 (batch numbering, context), DI-44/DI-46 (context); the audit trail SQL (anchors, checkpoints, kernel.verify_anchor).

Build:
1. Restore events and number safety (INV-27, INV-08): a `continuity.restore_event` record (restored-from backup id, backup time, restore time, operator, approver ids, affected chains, anchor comparison result, reason) written by a SECURITY DEFINER function, and a `continuity.after_restore(...)` procedure that bumps every GMP identifier sequence (batch numbers, contingency-form numbers, signature ids, user ids: discover sequences via a registry table `continuity.protected_sequence` that other modules register into, plus an allocation high-water mark kept OUTSIDE the restored database, simulated in tests by a separate file or second database) past the highest value ever issued, so numbers issued after the backup and lost in the restore are never reissued. A bypass test proves a number issued before a simulated restore cannot be issued again after it. Anchors: external anchors (kept outside the DB) that no longer match after a restore are covered by the signed restore event (verify: without the event, the anchor mismatch is reported as a problem; with it, it is reported as covered).
2. Batch-number allocation register in site services (`site` schema): allocation of batch numbers per product/site with a format rule, unique across both editions at the site (IN-18 context), never reused, voided numbers stay recorded with reason; allocation through a SECURITY DEFINER function; register its sequence as protected.
3. Backup/restore drill (DI-45): ops/backup/drill.sh (or a TS script run with tsx) that takes a pg_dump of a test database, restores it into an isolated new database, runs the kernel chain verification on both, and hash-compares records, audit trails and signatures tables (table-level ordered content hashes) between source and restore; writes a drill report (JSON + Markdown) under a path given as argument. A vitest test runs the drill end to end against a test DB (pg_dump/pg_restore 16 are installed at /usr/bin). Backup job failure raises an alarm (simulate a failing dump -> alarm row / non-zero exit plus report). "Delete a backup with production-admin credentials -> refused": model this as a design + test at the level you can: backup catalogue table where the app/admin role cannot delete rows, and document the storage-level WORM control in docs/operations.
4. DI-13 security baseline: (a) TLS: a production config validator in TS (packages/kernel/src/continuity/security-baseline.ts) that refuses a database URL without sslmode=verify-full/require and a server config without HTTPS, plus a pg_hba.conf template (hostssl only) in ops/; test that non-TLS config is refused; (b) kiosk hardening attestation: device classes SHARED/GRADE_A_B require a hardening attestation (USB mass storage blocked, kiosk mode) recorded before enrolment; model as data plus a check function in your schema, test refused enrolment without it (identity module B1 builds the device registry in parallel; keep your attestation table independent keyed by device uuid and the lead will wire the check into enrolment); (c) confidentiality of formulas: document the permission-based design (the identity module owns permissions), no code needed beyond a test-less note; (d) non-repudiation evidence package: document what it will contain (signature row, auth event, chain segment, seal) for Phase 1 exit; the lead will add the test after e-signatures land.
5. Documents (Phase 1 exit criteria): docs/security/threat-model.md (STRIDE per component: browser, API server, site gateway, database, site services, integrations, backups, admin console; each threat -> mitigation -> control/invariant IDs -> test or phase), docs/security/asvs-l2-review.md (OWASP ASVS 4.0.3 level 2 chapters V1-V14: status per requirement group for the design, gaps with owner and phase; paraphrase, no copying of ASVS text beyond short identifiers), docs/operations/ha-and-restore.md (HA topology, RPO/RTO targets as proposals for the owner, backup schedule, immutable storage, restore procedure with restore event and sequence bump, drill cadence, failover runbook including the clock-offset check), docs/operations/restore-drill-report-template.md. Keep them precise and short enough to review.
