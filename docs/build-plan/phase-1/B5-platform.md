# Module brief B5: trusted time, idempotency, outbox, state-machine engine (kernel)

Schema: `platform`. Migrations: packages/kernel/sql/0500_*.sql .. 0599_*.sql. Source: packages/kernel/src/time/, packages/kernel/src/commands/, packages/kernel/src/state/. Tests: packages/kernel/test/platform/. Migration filter: EBMR_MIGRATIONS='^(00|05)'.
Controls: DI-27. Invariant you own: INV-16 (the audit trail already takes recorded_at from the DB clock; you add the two-timestamp model for business events and its enforcement). Also: idempotency, outbox, state-machine engine with DB transition table and a consistency test (outline section 11 Phase 1 list).
Read: outline 5.6 (time), 5.7 (concurrency, idempotency), 5.2 intro and 5.2.2/5.2.3 (to see what state machines will look like), 4.4, 4.6 (outbox to integrations), 5.8; ADR 0006, 0010, 0012; control DI-27 and DI-28 (context).
Note: the ESLint rule already allows Date usage in packages/kernel/src/time/**; that is the only place in src where JS clock access may live, and the DB clock remains authoritative.

Build:
1. Two-timestamp model: a reusable SQL domain/type or column convention plus functions: `platform.check_occurred_at(occurred_at, trust, step_started_at, recorded_at)` enforcing occurred_at between step start and recorded_at and trust in DEVICE_SYNCED/DEVICE_UNSYNCED/USER_CLAIMED/PAPER; which time drives time constraints (occurred_at only when DEVICE_SYNCED, else recorded_at) and that choice recorded. Late-entry policy: late-entry window (policy value), beyond it needs a supervisor co-signature reference (uuid; signatures come from B2), and a late entry evaluates status guards at both instants (provide the helper that returns both instants to evaluate). A demo business table (stub_step_entry) showing the pattern with a bypass test: the app cannot set recorded_at (column default + trigger forcing clock_timestamp()).
2. Drift monitor: tables for time sources (validated configuration item: name, kind NTP, reference e.g. NPL/NIC traceable, validated_by, active) and drift samples (node, source, offset, recorded_at); a TS monitor function taking injected reference readings (no real NTP calls in tests) that records samples, raises an alarm when |offset| > threshold (policy, default 1 s, allowed 0.1-5 s) and, on loss of all references, raises an alarm; alarms go to a platform.alarm table and call a hook to create a DI incident (records module B4 builds incidents in parallel: define the call as a plain SQL function `platform.raise_time_incident(...)` in your schema that inserts into your own alarm table and emits an outbox message 'incident.requested'; the lead wires it to records.raise_incident later). Flag entries recorded within a drift window (a query/function). Monotonicity: a recorded_at earlier than the aggregate's last value is flagged; per-aggregate counters give order.
3. Site time: display helpers in TS converting UTC instants to site time with offset (Asia/Kolkata and a DST zone like Europe/Berlin for tests) using Intl only; durations computed from UTC instants; site-local calendar day for "daily" rules. DST-transition test (DI-27 catalog line). "Change a terminal clock, then record a step: stored time unaffected": prove that a client-supplied time never lands in recorded_at.
4. Idempotency: `platform.idempotency_key` table and a TS wrapper `withIdempotentCommand(pool, ctx, key, requestHash, work)` building on packages/kernel/src/db/command.ts `withCommand` (import it; do not edit it) so a retried command with the same key and same request hash returns the stored result without re-executing, and the same key with a different request hash is refused (EBMR-PLAT-xxx). Concurrency test: two parallel executions with the same key run the work once.
5. Outbox: `platform.outbox` (insert-only rows written in the same transaction as the business change, via `platform.enqueue(topic, aggregate, payload)`), a relay in TS that claims rows with FOR UPDATE SKIP LOCKED, delivers to a handler, records delivery attempts and marks delivered; at-least-once semantics with a consumer-side dedupe key. Tests: rollback of the business transaction leaves no outbox row; two relays never deliver the same row concurrently.
6. State-machine engine: DB transition table (machine code, machine version, from state, event, to state, guard codes, required signature meaning (nullable; signatures arrive with B2), required permission) and a SECURITY DEFINER `platform.transition(machine, aggregate_type, aggregate_id, event, expected_version, payload)` that locks the aggregate's state row, checks the transition exists for its pinned machine version, checks optimistic version, runs registered SQL guard functions by code, updates state and version, writes a history row and an outbox row, all in one transaction; the app role cannot update state rows directly (bypass test). TS side: XState 5 machine definitions (define one sample machine, e.g. a simplified record lifecycle DRAFT -> SUBMITTED -> CHECKED -> APPROVED -> SUPERSEDED/RETIRED) and a consistency test proving the XState definition and the DB transition table contain exactly the same transitions (a generator that emits the SQL seed rows from the XState definition is ideal, with a test that the committed seed matches the generated output). Machine versions are immutable once used; aggregates pin their machine version.
