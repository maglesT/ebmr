# Module brief B2: electronic signatures (kernel)

Schema: `esig`. Migrations: packages/kernel/sql/0200_*.sql .. 0299_*.sql. Source: packages/kernel/src/esig/. Tests: packages/kernel/test/esig/. Migration filter: EBMR_MIGRATIONS='^(00|01|02)' (you build on the identity module, which is complete: read packages/kernel/src/identity/README.md and its migrations 0100-0199 first; use its authentication service, authentication events, `iam.consume_auth_event`, `iam.assert_can_sign`, delegation and authority-evaluation functions; do not edit identity files: ask the lead in your final message if something is missing).
Controls: DI-35, DI-36, DI-37, DI-38. Invariants you own: INV-09, INV-10, INV-03 (generic mechanism: the verifier/witness is never a person who performed, entered data in or corrected the thing being verified), and the "signature IDs never reused" part of INV-27.
Read: outline 5.5 (all of it: challenge, authenticate, sign; components and sessions; meanings incl. WITNESSED vs VERIFIED; Part 11 administration; India DSC option is OFF in v1, just leave a documented extension point), 7.1, 7.2 (involvement set, S5, S6, S10, S16 no proxy signing), 5.4; ADR 0006 and 0012; the four control files.

Build:
1. Meanings catalogue (DI-35): a closed, versioned catalogue of signature meanings/types covering every predicate signature point listed in DI-35 (prepared, checked, QU-approved, issued, performed, verified, witnessed, supervised, container checked, charge-in verified, yield verified, IPC performed/verified, deviation authorised, correction, specimen approved, logbook performed/double-checked, production approved, packaging record approved, audit-trail reviewed, QU review/disposition, manufacturer release, market disposition, QP certification reference, true copy verified, void/reprint authorised, and any others the outline names). Each type: permitted roles/permissions, meaning text (paraphrased by us), independence rule (which earlier signers on the same object it must differ from, evaluated on the PERSON), re-authentication rule, WITNESSED constraints (same device or a device in the same room, within a window, default 5 min, before the next step starts: model the "next step started" as a parameter the caller supplies for now). Customers may add types; the minimum set cannot be removed or disabled (bypass test). No plain-acknowledgement path can complete a signature point (test: completing a "cleaning-log entry" stub that requires a signature with a plain ack is impossible).
2. Challenge: `esig.create_challenge(record ref (aggregate type + id + content version), meaning, client-displayed content hash)`; the server recomputes the canonical content hash from a canonical-content provider (define a SQL function registry per aggregate type; provide one for a stub signable table in your schema) and refuses if the hashes differ; challenge single-use, valid 120 s, bound to account, session, device; returns the manifestation preview.
3. Sign (SECURITY DEFINER, the only writer of signature rows; INV-10): consumes exactly one unused authentication event of the same person, bound to this challenge, with the components the policy requires (DI-38: two distinct components; default all components at every signing; the QA-approvable relaxation is a policy switch, default OFF, which applies only to routine signings by the session owner within one continuous session and then still needs the private component; never for disposition, certification or MBR approval; a signature by anyone other than the session owner always needs all components; the continuous session ends at lock, timeout, logout or terminal change), runs guards (role/permission at that instant via the identity module's authority evaluation which stores its evaluation (INV-26), delegation validity, independence/segregation on the person, performer-is-not-verifier (INV-03), record state via a caller-supplied expected state/version), inserts the signature row (content hash, auth event id, printed name AS AT SIGNING, user id, role, meaning, server time with UTC offset and site zone, challenge id), writes audit (the signature table is insert-only and audited) and seals the row with an HMAC or Ed25519 signature using a key from a key provider interface (test key in tests; KMS/HSM later; record key id and algorithm for agility). Any failure aborts everything.
4. Manifestation (DI-36): stored immutably with the signature; `esig.manifestation(signature_id)` for screen/print/PDF/export renderers; renaming a person later leaves historic manifestations unchanged (test).
5. Linking and invalidation (DI-37, INV-09): signatures bind the exact content hash; a permitted change to signed content (trigger on the stub signable table, and a generic mechanism other modules register their tables into) marks affected signatures SUPERSEDED_BY_CHANGE in the same transaction (via an insert-only invalidation row, not an update of the signature row), the element shows unsigned and re-signing is required; an integrity job `esig.verify_signatures()` re-computes content hashes and seals and detects any transplanted/copied signature row (test: copy a signature row to another record through the admin pool -> the integrity check fails).
6. Session rules tests (DI-38 catalog lines): sign twice in one session -> second needs at least the password (with the relaxation switch ON; with it OFF, both components); after timeout both components; applying the verifier's signature through the performer's session is refused.
7. Non-repudiation evidence package (DI-13 follow-up from the security module): `esig.evidence_package(signature_id)` returning the signature row, manifestation, the authentication event (components used, device, time, without secrets), the authority evaluation, the audit chain segment for the signed aggregate, the seal and its verification result. Tag its test [DI-13].

## Notes from the identity module (read packages/kernel/src/identity/README.md for details)
- Authentication events are created only through `authn_prepare`/`authn_finish`, callable only by the login role `ebmr_authn` (TS: `authenticate(...)` with a pool running as ebmr_authn; see test/identity/seed.ts `freshAuthEvent` / `withFreshAuth`).
- `iam.consume_auth_event(event, expected_person, expected_challenge, max_age)` is owner-only on purpose: call it from your SECURITY DEFINER signing function. An event may serve both its own command's attribution (INV-40) and one signature, but only within the same correlation id and transaction.
- Use `iam.assert_can_sign(account)`, `iam.resolve_signer(account, at)` (printed name and role as at signing), `iam.delegation_valid(...)`, `iam.evaluate_authority(...)` (stores the evaluation; INV-26), `iam.assert_segregated(rule, persons, subject)`, `iam.record_entry_persons(table, id)` / `iam.chain_persons(chain)` for involvement, and `iam.assert_not_administrator()`.
- Test identities: `seedActor(db, {roleCode, scope, deviceClass, roomCode, source, legalName, acknowledgeEsig, withBadge, withPin})`, `seedServiceActor(db, {kind, source})` from packages/kernel/test/identity/seed.ts. Use real role codes from the iam role catalogue. Every IAM function that changes an existing row needs reason_code in the actor context.
- Every SECURITY DEFINER function: `set search_path = pg_catalog, esig, iam, kernel, pg_temp` (pg_temp last; a repo-wide test enforces it) and schema-qualify catalog references.
- The lead is fixing, in parallel, a kernel gap where a session could forge `ebmr.ctx` with set_config and bypass begin_command; do not rely on `kernel.current_actor()` alone in your definer functions: call the identity module's validated-actor check (see its README, `iam.assert_validated_actor()` or equivalent).
- Other modules are complete (market, records, platform, continuity). The platform state engine has a SIGNATURE hook (`platform.register_hook`, signature `(uuid, text, text, text, jsonb) returns text`) that must check a signature is valid, not superseded, and bound to the record and meaning: implement that adapter function in your schema (read packages/kernel/src/state/README.md and 0500/0550 migrations). Your 02xx migrations run BEFORE the platform migrations (05xx), so do not call platform.register_hook in them; the lead registers the adapter in an integration migration (09xx). For your own test of the adapter you may register it inside the test through the admin pool (`set role ebmr_owner`), with the filter '^(00|01|02|05)'. The platform late-entry co-signature also goes through that hook.
- Records (B4) uses approval signature ids as plain uuids until you land; list in your final message which of its functions should verify them via your module.
