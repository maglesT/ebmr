# Module brief B4: records, retention, true copies, incidents, DI investigations (kernel)

Schema: `records`. Migrations: packages/kernel/sql/0400_*.sql .. 0499_*.sql. Source: packages/kernel/src/records/. Tests: packages/kernel/test/records/. Migration filter: EBMR_MIGRATIONS='^(00|04)'.
Controls: DI-01, DI-12, DI-47, DI-50. Invariant you own: INV-22.
Read: outline 3.3.6 (retention bullet: the full retention rule set and the retention dependency rule), 4.7 (CERT-In note for incidents), 5.4 (audit trail), 5.7 (evidence epoch, for "blocks disposition"), 4.4 (PostgreSQL) and anything on true copies/evidence export (search the outline for "true copy", "bundle", "PDF/A"); ADR 0007; control files for DI-01, DI-12, DI-47, DI-50 and also DI-24/DI-25 for context; the audit trail SQL (kernel.verify_chain, checkpoints).

Build:
1. DI-01 record-type register: record types (code, description, official record yes/no, raw data yes/no, GMP criticality, official medium ELECTRONIC/PAPER/HYBRID, storage location, owning module, retention key, whether it feeds an acceptance limit). A classification of a data item as "informational" when it feeds an acceptance limit is refused by a validation function other modules (the MBR validator in Phase 2) will call: provide `records.assert_classification_valid(...)` and a test that mimics "approve an MBR with an IPC result classified informational -> blocked" using a stub MBR element table (stub_*).
2. Retention (DI-47, INV-22): a retention schedule per record instance (record type, aggregate id, the dates that drive retention: manufacture, expiry, distribution, EU QP certification date (nullable = OPEN), disposition date, abort/cancel date, licence form predicate), computed retain_until = the latest of every rule that applies (implement the rule set in outline 3.3.6 as a pure TS function with exact date arithmetic in the site calendar; mirror the decision logic in SQL or store the TS result with its inputs and rule version; say which and why). Retention OPEN while an EU certification date is pending. Retention dependency: a shared/supporting record inherits the maximum retain_until over its dependants, recomputed when a dependant's dates change (test: a component lot used by two batches with different expiries follows the later one). Legal holds and DI-investigation holds block disposal. Purge only through `records.purge(...)` (SECURITY DEFINER): refuses before retain_until or while on hold; leaves a tombstone row (what was purged, hashes, retain_until, approvals) and a chain checkpoint (kernel.checkpoint_chain) before purging. The application role cannot delete GMP rows directly (bypass tests on a stub record table registered with kernel.register_audited_table). Note: the retention rule values themselves will come from the market-profile engine (B3) later; for now keep the rule parameters in one clearly marked data structure with sources so the lead can wire them to rule keys.
3. True-copy bundle and verifier: a TS module that, for a given aggregate (chain key) and a set of record rows, produces a bundle (JSON manifest + canonical record content + the audit chain segment + chain verification result + SHA-256 of each part + a manifest hash; PDF rendering comes in Phase 4) and a verifier (library function plus a small CLI entry `packages/kernel/src/records/verify-true-copy.ts` usable with tsx) that re-computes every hash and the chain links offline and reports any mismatch. Tests: tamper with one byte in the bundle -> verifier reports it; a bundle of a real chain from the test DB verifies.
4. DI-12 incidents: incident register (type, severity MINOR/MAJOR/CRITICAL, source e.g. INTERFACE_FAILURE, TIME_SYNC, SECURITY, DATA_INTEGRITY; linked batches/records by aggregate type and id; CERT-In reportable flag with the 6-hour reporting deadline and reported-at, marked "verify" as in the outline); states OPEN -> UNDER_INVESTIGATION -> CLOSED; closing a CRITICAL (or MAJOR) incident requires a root cause and a CAPA reference (refused otherwise, enforced in the DB function); a function `records.open_blockers(aggregate_type, aggregate_id)` that returns open incidents/investigations/holds blocking disposition, for the release module later. Test the catalog line with a simulated "balance interface killed mid-weighing" event that calls `records.raise_incident(...)` from a SYSTEM actor.
5. DI-50 DI investigations: open an investigation for a person (user) and a date range; `records.investigation_scope(...)` lists every record (from kernel.audit_event) that person created or changed in the range, with aggregate ids; linked batches are blocked from disposition (appear in open_blockers) until closed; closing needs conclusion, remediation and approver different from the investigator.
Register every GMP table with kernel.register_audited_table; incidents, holds and tombstones are GMP records.
